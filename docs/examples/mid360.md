# Evaluate MID-360 ROS 2 bags

ROS 2 Jazzy bags can be evaluated directly, without installing ROS or replaying
the bags. Both SQLite3 (`.db3`) and MCAP storage are supported. Pass the bag
**directory containing `metadata.yaml`**, rather than an individual storage file.
The LiDAR topic may contain `sensor_msgs/msg/PointCloud2` or Livox
`livox_ros_driver2/msg/CustomMsg` messages.

## Build the three pipelines

Use Python 3.12, a C++20 compiler, CMake 3.24–3.x, and the development packages for
Eigen 3.4, Sophus 1.24.6, oneTBB, robin-map, Ceres 2.2 and GTSAM 4.2 with Boost.
On Debian/Ubuntu the distribution packages provide most dependencies:

```sh
sudo apt-get install build-essential ninja-build libeigen3-dev libtbb-dev \
    robin-map-dev libceres-dev libboost-serialization-dev libboost-system-dev \
    libboost-filesystem-dev libboost-thread-dev libboost-date-time-dev \
    libboost-timer-dev libboost-regex-dev libboost-program-options-dev
```

Install Sophus and GTSAM separately if they are not available on your system.
For GTSAM use `-DGTSAM_USE_SYSTEM_EIGEN=ON`; disable its tests, examples and Python
bindings when only building these pipelines. When installing dependencies into a
custom prefix, export `CMAKE_PREFIX_PATH` and, for shared libraries,
`LD_LIBRARY_PATH` to include that prefix. Then, from the evalio repository:

```sh
bash scripts/setup_rosbag_pipelines.sh
```

This clones the three pinned upstream versions, applies evalio's integration
patches, and builds the local checkout. It preserves existing source changes and
does not stash or reset checkouts. `evalio ls pipelines` must list `kiss`, `ct`
and `form`. Rerun this script after editing C++ code. The installation uses a
wheel; rerun it after Python changes too, or use `PYTHONPATH=python` with the
copied extension to run Python source changes.

## Run garden1, garden2 and garden3

[`examples/mid360-garden.yml`](https://github.com/taku0625/evalio/blob/feat/rosbag-evaluation/examples/mid360-garden.yml)
contains the three paths under `/home/nakao/dataset/rosbag/ral2026`. Set the
`lidar_topic: &lidar_topic ...` value on garden1 to the topic in your bags. The
garden2 and garden3 entries reference it with `lidar_topic: *lidar_topic`, so a
single edit updates all three. The sample uses `/livox/lidar_192_168_1_182`.
If a bag has a different topic, replace its alias with an explicit topic. An
omitted `lidar_topic` uses the loader default `/livox/lidar`. Then run:

```sh
uv run --no-sync evalio run -c examples/mid360-garden.yml
uv run --no-sync evalio stats results/mid360-garden
```

There are nine experiments: three bags times three methods. Outputs are stored
as `results/mid360-garden/rosbag/garden1/{kiss,ct,form}.csv` and likewise for the
other bags. Existing completed experiments are skipped; failed experiments
require `--rerun-failed`. Use a new output directory (`-o results/new-run`) when
changing preprocessing or pipeline parameters to avoid reusing older results.
Missing paths/topics and pipeline failures return a nonzero exit status.

To run a shorter check, add `length: 100` to each dataset entry in the YAML.
Bag and ground-truth paths can be absolute or relative to the config file.
Output directories are relative to the current working directory.

## MID-360 preprocessing and timing

The loader projects returns into a spherical grid (default: 32 elevation rows,
512 azimuth columns, elevations −7° to 52°). It keeps the closest return per
cell and pads missing cells with zero-range points. This gives FORM the organized
input it requires. KissICP and CT-ICP discard the padding. These angular bins are
a preprocessing choice for the MID-360's nonrepetitive pattern; tune resolution
and elevation limits for your mounting and data. They are not native scan rings.

Livox `CustomMsg` point offsets are nanoseconds relative to the header timestamp.
For `PointCloud2`, the loader recognizes `offset_time`, `timestamp`, `time`, and
`t`; integer time fields default to nanoseconds and floating fields to seconds.
Set `time_field` and `time_unit` (`s`, `ms`, `us`, `ns`) on a dataset entry when
needed. Epoch timestamps are converted to offsets from the message header.
The loader respects row padding and byte order. Header timestamps must mark the
start of the scan.

When point times are absent, all offsets are zero. The sample config uses rigid
CT-ICP (`motion_compensation: NONE`, `distance: POINT_TO_PLANE`) and KissICP
without deskewing. For actual continuous-time CT-ICP on timed messages, set
`motion_compensation: CONTINUOUS` and `distance: CT_POINT_TO_PLANE`. Do not enable
continuous-time compensation or deskewing on untimed clouds.

These three pipelines use LiDAR only. An optional `imu_topic: /livox/imu` reads
IMU messages, but they are not fused by these methods. Output poses are in the
LiDAR frame.

## Accuracy metrics

Set `ground_truth: /path/to/garden1.tum` on each dataset entry to compute ATE and
RTE with `evalio stats`. TUM files contain
`timestamp tx ty tz qx qy qz qw`, with seconds in the bag clock and poses of the
LiDAR frame. Transform ground truth from other sensor frames before using it.
Without ground truth, trajectories, processing times and completion statuses are
available; absolute/relative accuracy cannot be measured.

## Verify the installation

```sh
uv run --no-sync pytest tests/test_local_rosbag.py -v
```

The tests write Jazzy bags in SQLite3 and MCAP with both supported message types,
check timestamps and projection, and run all compiled pipelines on a generated
moving scan sequence. A missing compiled pipeline is reported as a skipped test;
the build script checks that all three are available before evaluation.
